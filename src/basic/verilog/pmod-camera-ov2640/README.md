# OV2640 DVP 功能验证 (iCESugar + iCE40UP5K + PMOD-CAMERA)

> 英文版见 [`README_en.md`](README_en.md)（内容一一对应，方便国外的朋友阅读）。

在 iCESugar (iCE40UP5K-SG48I) 上驱动 PMOD-CAMERA 上的 **OV2640** 模组。
上电后自动完成"SCCB 配置 -> 回读关键寄存器 -> 统计 1 秒 DVP 出流 -> 字节序判定"，
最后用 9600 8N1 从 UART 打印一份自检报告。

目的只有两个：**确认 SCCB 通信正常**、**确认 DVP 真的在出流**。

当前状态：

- **自检已实机验证通过**（`verdict = 15` = 0b01111，五项结论全绿，报告见第 5 节）。
- **拍照链路已跑通**：60 段 / 538 包 / 0 个 CRC 错误，640x480 YUYV，
  几何和字节序都用**彩色测试条**交叉验证过（第 5.3 节）。
- **画面已经出来了**：2026-11-23 白天复测，640x480 真实场景（人像 + 货架 +
  百叶窗），Y 通道均值 **101.4**、标准差 71.8，U/V 均值 125/127（不偏色），
  曝光正常。
- **自动曝光也能用**：OV2640 的片上 AE 引擎要求**整块 AE 参数
  （COM8/COM9/AEW/AEB/VV/16 区权重/直方图）写在寄存器表的最末尾**，
  写在表头会被复位序列清掉 —— 四组对照实验见第 5.5 节。

> 本工程是 [`pmod-camera-ov5640`](../pmod-camera-ov5640/) 的 OV2640 版本，
> 结构、协议、踩过的坑大部分通用；**OV2640 特有的坑集中列在第 7 节**。

## 1. 硬件连接

引脚映射和 OV5640 工程**完全一致**（只换了 PMOD-CAMERA 上的摄像头模组）：

| FPGA 引脚 | 信号 | 方向 | 说明 |
|---|---|---|---|
| 35 | clk12 | in | 板载 12MHz (iCELink MCO 经 ICE_CLK) |
| 43 | XMCLK | out | 24MHz (PLL 12->24, IOB DDR 50% 占空) |
| 44 | PCLK | in | DVP 像素时钟 (接成全局时钟) |
| 38 | VSYNC | in | DVP 场同步 |
| 42 | HREF | in | DVP 行同步 |
| 37 | SCL | bidir | SCCB 时钟 (开漏 + 内部上拉) |
| 36 | SDA | bidir | SCCB 数据 (开漏 + 内部上拉) |
| 23 / 25 / 26 / 27 / 28 / 31 / 32 / 34 | D0..D7 | in | DVP 数据 Y2..Y9 (PMOD3) |
| 6 | TX | out | UART 输出 (iCELink CDC, 9600 8N1) |
| 40 / 41 / 39 | LED_R/G/B | out | 绿=全通过, 红=有失败, 蓝=工作中 |

SCCB 两根线用开漏物理层：`SB_IO PIN_TYPE=6'b1010_01` + `D_OUT_0=0` +
`OUTPUT_ENABLE=*_low` + `PULLUP=1`，由 FPGA 拉低、从机/上拉释放。

引脚依据 `src/common/io.pcf` 与 `schematic/pmod-camera-v1.0.pdf` 核对。

**XMCLK 是 FPGA 给的 24MHz**（12MHz 进 PLL 倍频到 24MHz，再用 IOB 的 DDR 输出
产生 50% 占空方波）。OV2640 要求 24MHz，不要改成 12MHz。

## 2. OV2640 和 OV5640 的关键差异

**这几条不一样，直接照抄 OV5640 的代码一定跑不起来。**

| 项 | OV5640 | **OV2640** |
|---|---|---|
| SCCB 从机地址 (写) | 0x78 (7bit 0x3C) | **0x60 (7bit 0x30)** |
| SCCB 从机地址 (读) | 0x79 | **0x61** |
| 寄存器地址宽度 | 16 位 (0x3xxx) | **8 位 (0x00..0xFF)** |
| 寄存器 bank | 没有 | **有**：写 `0xFF`=0x00 选 DSP bank，0xFF=0x01 选 sensor bank |
| 芯片 ID | 0x300A / 0x300B = 0x56 / 0x40 | **切到 bank1 后读 0x0A / 0x0B = 0x26 / 0x42** |
| 输出尺寸寄存器 | 0x3808~0x380B 直接就是输出宽高 | **0xC0/0xC1 是"输入"尺寸，0x5A/0x5B 才是"输出"尺寸** |

最后一条是 OV2640 最容易踩的坑，单独展开。

### 2.1 尺寸寄存器：输入 vs 输出

OV2640 的 DSP 有两级尺寸：

- **输入（相机读出来的那一帧有多大）**：
  `HSIZE8(0xC0) = 宽>>3`、`VSIZE8(0xC1) = 高>>3`、
  `HSIZE(0x51) = 宽>>2`、`VSIZE(0x52) = 高>>2`（4 像素单位）
- **输出（缩放之后 DVP 上真正吐出多少像素）**：
  `ZMOW(0x5A)` / `ZMOH(0x5B)` / `ZMHH(0x5C)`（4 像素单位，12 bit），
  以及 `CTRLI(0x50)` 的 H/V 预分频

Linux 内核、Zephyr、OpenMV、esp32-camera **四个独立驱动对这点的定义完全一致**。
本工程用的是内核那条路线（UXGA 读出 -> DSP 缩放到 VGA）：

```
输入:  HSIZE8 = 1600>>3 = 200 = 0xC8    VSIZE8 = 1200>>3 = 150 = 0x96
       HSIZE  = 1600>>2 = 400 -> 0x90    VSIZE  = 1200>>2 = 300 -> 0x2C
输出:  ZMOW   =  640>>2 = 160 = 0xA0     ZMOH   =  480>>2 = 120 = 0x78
       ZMHH   = 0x00                      CTRLI  = 0x80 (h_div=0, v_div=0)
```

**写错的后果**：把 `HSIZE8/VSIZE8` 直接写成 640/480 的值（0x50/0x3C），
芯片会去读一个根本不存在的窗口，画面是花的或者干脆不出流。

### 2.2 改尺寸/改时钟要用 R_BYPASS 括起来

```
写 0x05 = 0x01   (R_BYPASS: 旁路 DSP, 传感器直通)
  ...改 HSIZE8/VSIZE8/HSIZE/VSIZE/ZMOW/ZMOH/R_DVP_SP...
写 0x05 = 0x00   (R_BYPASS: 恢复走 DSP)
```

OpenMV 和 esp32-camera 都这么做；Linux 内核省略了这一步（改用 `RESET_DVP`）。
本工程**两边都做**（`RESET_DVP` + `R_BYPASS` 括号），实测一次通过。

### 2.3 字节序

`IMAGE_MODE(0xDA) = 0x00` -> 总线是 **YUYV**（高字节先，第一个字节就是 Y）。
`bit0 = 1` 才是 UYVY。`CTRL0(0xC2) bit4` 交换 U/V（YUYV <-> YVYU）。

## 3. 构建

```bash
cd src/basic/verilog/pmod-camera-ov2640

make                # 自检固件 (9600 baud 打印报表)
make photo          # 拍照固件 (115200 baud, 60 段 x 8 行)
make sim            # 离线仿真报表展开 (iverilog, 不需要硬件)
make sim_photo      # 拍照模式的离线仿真
```

需要 yosys / nextpnr-ice40 / icetime / icepack。
`ov2640_cfg.hex` 与 `text.hex` 由 `gen_cfg_hex.py` / `gen_text_hex.py` 自动生成。

资源占用与时序（`nextpnr-ice40 --up5k --package sg48` + `icetime`，实测）：

| 项 | 自检 `make` | 拍照 `make photo` |
|---|---|---|
| ICESTORM_LC (逻辑) | **4999 / 5280 (94%)** | 1389 / 5280 (26%) |
| ICESTORM_RAM (SB_RAM40_4K) | 8 / 30 (26%) | **24 / 30 (80%)** |
| SB_IO | 19 / 96 (19%) | 19 / 96 (19%) |
| SB_GB | 8 / 8 (100%) | 8 / 8 (100%) |
| icetime | **38.19 ns / 26.18 MHz PASSED**（约束 24 MHz） | **28.44 ns / 35.16 MHz PASSED** |
| 固件 | `top.bin` 104090 字节, md5 `a8558270b4a0e09ee870ae9378861097` | `top_photo.bin` 104090 字节, md5 `e7459780eab86639764655804b62894d` |
| 配置 ROM | `ov2640_cfg.hex` 230 条, md5 `cee3afd62e9e9be21cce721679bba93e` | 同左 |

> **自检固件的逻辑已经占到 94%**（4999/5280），再加功能要省着用；
> 拍照固件的瓶颈是 RAM（80%，其中行缓冲占 20 块）。

**没有帧率参数**：OV2640 的帧率由 `CLKRC(0x11)` / `R_DVP_SP(0xD3)` / `FLL(0x46)`
决定，不是 OV5640 那种改一个预分频寄存器就完事，所以没有 `make FPS=30` 这种开关。

## 4. 烧录与看结果

iCELink 的 HID 命令行工具（**不要拖拽烧录**，虚拟 U 盘不可靠）：

```
# 仓库根目录下的 tools/src/icesprog
tools/src/icesprog src/basic/verilog/pmod-camera-ov2640/top.bin
```

**顺序很重要**：本设计跑一次测量就停在 ST_DONE，不会自己重跑。
所以要先烧录（烧录会让 DAPLink 复位目标，FPGA 重新开始测量），
再开串口收数 —— 复位后大约 8 秒才开始打印。

Windows 侧建议用 pyserial 紧密循环收，**不要用 PowerShell 的
`System.IO.Ports.SerialPort.Read`**（它每次调用会阻塞满 ReadTimeout，
9600bps 下会成片丢数据）：

```python
import serial, time
ser = serial.Serial('COM419', 9600, timeout=0.05)
buf = bytearray()
t0 = time.time()
while time.time() - t0 < 30:
    d = ser.read(4096)
    if d:
        buf.extend(d)
print(buf.decode('ascii', 'replace'))
```

### 5.3 白天复测：真实画面出来了

2026-11-23 上午在实验室重测（**灯已开、镜头保护膜已撕**），自动曝光拍到办公室实景：
前景一个人像，背景是货架上的档案盒和左侧百叶窗。

| 通道 | min | max | mean | std |
|---|---|---|---|---|
| Y | 0 | 255 | **101.4** | 71.8 |
| U | 71 | 184 | 125.1 | 11.5 |
| V | 79 | 192 | 126.9 | 11.5 |

判读：

- **Y 均值 101.4** 落在正常照片区间（理想中灰 110~120 附近），**不是**过曝也不是欠曝；
- U/V 均值 125/127 —— 几乎就是色度中点，说明**白平衡没有偏色**（人脸肤色自然）；
- 画面里能看清人脸五官、货架标签和百叶窗条纹，**不是**糊的也不是噪声堆；
- 逐行亮度从上到下 146 → 30 的自然过渡，和真实房间的明暗分布一致；
- 横向撕裂是**分段扫描的固有代价**（每帧取 8 行、60 段来自 60 个不同帧），
  静止物体没问题，人脸在动就会有拖影 —— 这是协议决定的，不是 bug。

### 5.4 曝光怎么调

默认走**自动曝光**（片上引擎，见 5.5），不用手调。
如果场景特别亮/特别暗、想要完全确定的曝光，也可以切到**手动**：
把 `ov2640_end_regs` 里的 `COM8` 改成 `0xE0`（关掉 AGC/AEC），
再自己写 `GAIN(0x00)` 和 `AEC(0x10)`。

GAIN 的换算公式（datasheet）：
`Gain = (B7+1)x(B6+1)x(B5+1)x(B4+1)x(1 + B3:0/16)`，范围 1x~32x。

| 配置 | GAIN | 倍数 | AEC | 实测 Y 均值 | 备注 |
|---|---|---|---|---|---|
| **自动（默认）** | 引擎 | — | 引擎 | **101.4** | ✅ 随光照自适应，推荐 |
| 手动 | `0xFF` | 32x | `0xFF` | 175.2 | **过曝**，高光一片死白 |
| 手动 | `0x7E` | 15x | `0xFF` | 99.7 | ✅ 室内白天也够用 |
| 手动 | `0x38` | 6x | `0xFF` | 更暗 | 强光 / 室外 |
| 手动 | `0x18` | 2x | `0xFF` | 很暗 | 极亮环境 |

> AEC 是 **16 位跨 3 个寄存器**：`REG45(0x45)[5:0]` = AEC[15:10]、
> `AEC(0x10)[7:0]` = AEC[9:2]、`REG04(0x04)[1:0]` = AEC[1:0]。
> 只写 `0x10` 只能控制低 8 位（= AEC[9:2]），上限 0xFF 即 AEC=1020。
> 改曝光只要改 `ov2640_regs.h` 里 `ov2640_end_regs` 那几行，然后
> `python3 gen_cfg_hex.py ov2640_regs.h ov2640_cfg.hex && make && make photo`。

### 5.5 自动曝光引擎：四组对照实验（根因找到了）

OV2640 片上有 AE/AWB 引擎（`COM8` 的 `AEC_EN`/`AGC_EN` 打开它）。
本工程把它彻底试了一遍，四组对照全部是同一场景、同一光：

| # | 寄存器表末尾怎么写 | 回读 GAIN / AEC | 画面 |
|---|---|---|---|
| 1 | 内核原序（`COM8=0xE5` 写在表头） | `0x01` / `0x4E`（出厂默认） | 夜间全黑，引擎压根没接管 |
| 2 | 只在末尾补写 `COM8=0xE5`（其余 AE 参数仍在表头） | `0x01` / `0x4E` → 引擎顶到 `0xFF`/`0xFF` | 过曝，Y=175.2 |
| 3 | 整个 AE 块搬到末尾（`AEW=0x40 AEB=0x38`） | `0x03` / `0x38`（爬坡中） | 正常量级 |
| 4 | 整个 AE 块搬到末尾（`AEW=0xFF AEB=0x00`）✅ **默认** | `0x03` / `0x38`（爬坡中） | **正常，Y=101.4** |

**根因：OV2640 在复位序列之后会把自己的 AE 配置恢复成默认值，
所以 `COM8` / `COM9` / `AEW` / `AEB` / `VV` / 16 区测光权重 / 直方图上下限
这一整块 AE 参数，必须写在寄存器表的最后（复位之后）。**

- 实验 1 → 2：只把 `COM8` 挪到末尾，引擎接管了，但它用的是复位后的默认参数，
  于是一路把增益和曝光顶到满量程 → 过曝；
- 实验 2 → 4：把**整块** AE 参数都挪到末尾，引擎拿到的参数才是对的 → 曝光正常；
- 实验 3 vs 4：`AEW`/`AEB` 取哪组值结果**完全一样**（回读一模一样），
  说明起决定作用的不是这两个寄存器的数值，而是**整块 AE 参数的位置**；
- 实验 1 的另一个佐证：引擎没接管时回读是出厂默认 `0x01`/`0x4E`，
  而手动模式下写 `GAIN=0x7E` 回读就是 `0x7E` —— 回读链路本身没问题。

### 5.6 结论

- ✅ SCCB 通信正常、寄存器读写和回读正常（`reads ok=12/12`，`nack tx=0`）；
- ✅ DVP 真的在出流，640x480 YUYV，字节序、几何、时序全部核对无误；
- ✅ **能拍出正常曝光的真实画面**（Y 均值 101.4，色度不偏）；
- ✅ **片上自动曝光可以用**，前提是 AE 参数块写在寄存器表末尾（5.5）。

## 7. OV2640 踩过的坑（留给后来人）

> OV5640 工程那 26 条坑（时序/复位/资源/CRC/BRAM 之类）对 OV2640 同样适用，
> 这里只列 **OV2640 特有的**。

1. **OV2640 的寄存器地址只有 1 个字节，OV5640 的 `sccb_master` 是按 16 位发的**。
   OV5640 那个版本一次发 `reg[15:8] + reg[7:0]` 两个地址字节；
   OV2640 上这么发，等于**把寄存器地址当成数据写进去了** ——
   表现是"写不进任何寄存器，但 SCCB 有应答"。
   解决办法：`sccb_master` 加一个 `ADDR8` 参数，8 位模式下只发 1 个地址字节，
   并且读写事务的字节序号判断也跟着改
   (`写: bi==2 发完数据就 STOP`，`读: bi==1 发完寄存器就转读相`)。
   本工程 OV2640 目录里的 `sccb_master.v` 默认 `ADDR8 = 1`。

2. **芯片 ID 在 bank1，读之前必须先切 bank**。
   OV2640 的 `0xFF` 是 bank 选择寄存器：写 `0xFF=0x00` 进 DSP bank，
   写 `0xFF=0x01` 进 sensor bank。`PID(0x0A)` / `VER(0x0B)` 在 sensor bank，
   而 `IMAGE_MODE(0xDA)` / `ZMOW(0x5A)` 在 DSP bank。
   所以诊断读不能像 OV5640 那样"一口气连读 12 个地址"，
   本工程改成了 **14 步：1 次写切 bank + 4 次读 + 1 次写切回 bank + 8 次读**。
   忘了切 bank 的症状是：读回来的全是 0x00 或者上一次 bank 的值。

3. **配置 ROM 绝对不能按地址去重**。
   OV5640 的 `gen_cfg_hex.py` 会把"同一个地址写多次"合并成最后一次 ——
   那是安全的，因为 OV5640 的寄存器地址是唯一的。
   OV2640 不行：`0xFF` 在两个 bank 里是两个不同的寄存器，
   而且 `BPDATA(0x7D)` 连续写时靠的是芯片内部的**地址自增**
   (`0x7C=0x03, 0x7D=0x48, 0x7D=0x48, 0x7C=0x08, 0x7D=0x20, ...`)，
   一旦合并顺序就会写坏。OV2640 的生成器严格按表里的顺序原样输出。

4. **软复位之后必须延时**。
   OV2640 上电后**不出图**，必须写完整张寄存器表；
   而 `COM7(0x12)=0x80` 的软复位之后，所有寄存器回到出厂值，
   整张表要重新写一遍 —— 这中间芯片需要时间复位。
   所以 ROM 里加了第 4 种操作码 **op=3 "延时 N 毫秒"**，
   `ov2640_cfg.v` 里对应一个 `S_DELAY` 状态。
   少了这一步，轻则复位没生效，重则后面的写全部落空。

5. **`ov2640_regs.h` 里的值必须写成 0x 十六进制**。
   这个坑我自己踩了一次：延时伪指令写成 `{ 0xFF00, 5 }`（十进制），
   生成器的正则只认 `0x` 开头的，**结果整条延时指令被静默跳过**，
   程序不报错、ROM 照样生成，只是少了那个等待。
   现在的生成器会数一遍表里写了几项、解析出几项，对不上直接报错。

6. **别把 `HSIZE8/VSIZE8` 当成输出尺寸**（见第 2.1 节）。
   正确做法是输入 1600x1200、输出 ZMOW/ZMOH = 640x480。

7. **`CLKRC(0x11)` 和 `R_DVP_SP(0xD3)` 的语义公开资料对不上**。
   四个驱动给出的取值互相矛盾（`CLKRC` 有 0x00 / 0x01 / 0x07 / 0x80 四种，
   `R_DVP_SP` 有"手动 0x02"和"自动 0x80"两种），
   对 PCLK 频率的模型也有两种（差 1.5~3 倍）。
   本工程用内核那套（`CLKRC=0x00` + `R_DVP_SP=0x02`），
   **实测 PCLK = 33MHz**，640x480 @ 14fps，够用。
   要调帧率就改这两个寄存器，改完重跑自检看报表里的 `pclk`。
   `CLKRC` 的 bit7 到底是"PLL 使能"还是"2 倍频"，公开资料仍然对不上。

8. **`REG04(0x04)` 的 bit[1:0] 是 AEC 曝光值的低 2 bit**，改镜像的时候别覆盖掉。
   镜像位是 bit7 (HFLIP) / bit6 (VFLIP)，翻转竖直方向时还要同时置 bit4 (VREF_EN)，
   否则会出现红绿条纹（Linux 内核 2006 年的一个补丁专门讲这件事）。

9. **画面方向取决于模组镜头的装配方向，不是硅片本身**。
   OV2640 是 **FSI**（前照式）传感器，读出方向本身不镜像；
   但模组厂商装镜头时可能上下颠倒 180°。
   Linux / esp32 / Zephyr 三个驱动的默认值都是 `REG04 = 0x28`（不翻转），
   但 OpenMV2 和 mikroPhone 的默认表里是 `0xF8`（全开翻转）。
   **判断方法**：拍一张**有人脸**的照片 —— 鼻子朝画面左边、耳朵在脸的右边
   就是正常方向（看到的是他/她的左耳）；鼻子朝右、耳朵在左就是被镜像了。

10. **改尺寸之后第一帧可能是花的**。OV2640 的 AWB/AEC 需要 10~20 帧才收敛，
    刚上电那几帧偏绿是正常的。自检工程会等 6 个场同步边沿再回读寄存器，
    拍照工程每段采的是不同帧，凑满 60 段时白平衡早就稳定了。

11. **画面全黑时，先看 `GAIN(0x00)` / `AEC(0x10)` 这两个测光寄存器**。
    这是 OV2640 判断"自动曝光到底有没有在动"的第一手证据：

    * `GAIN` 一直是 `0x00/0x01`（最小）、`AEC` 一直很小
      -> 芯片认为场景**很亮**，但实际是黑的，说明测光输入和真实图像对不上。
    * `GAIN` 到了 `0x3C` 以上、`AEC` 也变大
      -> 芯片认为场景**很暗**，正在拼命拉曝光，但画面还是黑的，
      那就是模拟通路/模组本身的问题（镜头被遮、模组装反、坏了）。

    本工程第一次抓到全黑时是 `GAIN=0x01 / AEC=0x4E`（都停在最小），
    而当时**实验室没开灯**——环境暗成那样，自动曝光却认为"很亮"，这本身就说明
    自动曝光没有正常工作。**在排查任何 OV2640 "黑图"问题之前，
    一定要先把这张报表里的 GAIN/AEC 读出来看一眼。**

12. **用 `COM7(0x12)` 的 bit1 (0x02) 打开彩色测试条，是定位"黑图"最省事的办法**。
    `COM7 = 0x04 | 0x02 = 0x06` 打开的是芯片内部的测试图发生器，
    画面直接绕过传感器模拟通路。
    彩条正常 = FPGA 采集链路没问题，问题在传感器一侧；
    彩条也不对 = 回去查 DVP 时序/字节序/引脚。
    本工程就是靠这一招把范围缩到"只剩模拟/测光问题"的（第 5.2 节）。

13. **esp32-camera 和 Linux 内核的模拟寄存器组有两处不一致，换模组时可以试**。
    同样是 OV2640，两份表在这两个 sensor bank 寄存器上取值不同：

    | 寄存器 | Linux 内核 | esp32-camera (UXGA) |
    |---|---|---|
    | `0x39` | `0x02` | `0x82` |
    | `0x06` | `0x02` 然后 `0x88`（最终 0x88） | `0x02`（最终 0x02） |

    其余模拟寄存器（`0x35` / `0x22` / `0x37` / `0x34` / `0x0D` / `0x0E` / `0x42`）
    两边在 UXGA 档位是一致的。
    如果换了模组之后画面还是不对，把这两处改成 esp32-camera 的取值试一轮，
    每次改完重跑自检、看报表里的 GAIN/AEC 有没有变化，
    就能知道是哪个寄存器在起作用。

14. **强制手动曝光/增益是判断"模拟通路通不通"的最快办法**。
    在 `ov2640_regs.h` 的 `ov2640_end_regs` 末尾加三行：

    ```c
    { 0xFF, 0x01 },     // BANK_SEL = sensor bank
    { 0x13, 0xE0 },     // COM8: 清掉 AGC_EN(0x04) / AEC_EN(0x01) -> 手动模式
    { 0x00, 0x3C },     // GAIN  手动增益
    { 0x10, 0x80 },     // AEC   手动曝光
    { 0xFF, 0x00 },     // BANK_SEL = DSP bank
    ```

    手动模式下 GAIN/AEC 回读值 == 写进去的值，可以确认这两个寄存器
    确实是可写可读的（自检报表里会打印它们）。
    如果拉到最大增益 + 最长曝光画面还是黑的，那基本可以排除
    "自动曝光没收敛"这个方向，直接去查模组/镜头/装配。

### 坑 15：OV2640 的**整块 AE 参数必须写在寄存器表的最后**

`COM8` 的 bit0 = `AEC_EN`、bit2 = `AGC_EN`，是片上 AE/AWB 引擎的开关；
`COM9`（AGC 上限）、`AEW`/`AEB`（稳定工作区间）、`VV`、16 区测光权重
（`0x5D~0x60`）、直方图上下限（`0x61`/`0x62`）则是引擎的算法参数。

**芯片在复位序列之后会把这套配置恢复成默认值**，所以按 Linux 内核的顺序
把它们写在表头，等于全部作废：

- 只在表头写 `COM8=0xE5` → 回读 `GAIN=0x01`/`AEC=0x4E`（出厂默认），
  引擎没接管，夜里拍出来全黑；
- 只在表尾补 `COM8=0xE5` → 引擎接管了，但参数是复位后的默认值，
  增益和曝光一路顶到 32x 满量程 → 过曝；
- **把整块 AE 参数都挪到表尾** → 引擎参数正确 → 曝光正常（Y 均值 101.4）。

### 坑 16：`AEW`/`AEB` 的**数值**不重要，重要的是**位置**

`AEW=0x40 AEB=0x38`（内核值）和 `AEW=0xFF AEB=0x00`（放开区间）实测结果
**完全一样**（回读的 GAIN/AEC 一模一样，画面也一样）。
所以别去纠结这两个寄存器该填几，先保证整块 AE 参数写在复位之后。

### 坑 17：回读 `GAIN`/`AEC` 前，先用**手动模式**证明写入本身是通的

`GAIN=0x01` / `AEC=0x4E` 有两种完全不同的成因：
(a) 芯片自己写的（AE 引擎接管了），(b) 我们的写根本没生效。
分不清就会得出"回读链路坏了"或者"引擎没工作"这种错误结论。
可靠做法：先 `COM8=0xE0`（关引擎）写 `GAIN=0x7E`，回读必须是 `0x7E`；
再打开引擎重测，回读变了才说明是引擎写的。

### 坑 18：回读的**时机**：末尾至少留 255 ms，而且读到的是**爬坡中**的值

引擎收敛要几帧时间（640x480 下 ~14 fps，3~4 帧 = 200~300 ms）。
末尾延时只有 50 ms 时读到的是收敛**前**的出厂值，会误判成"引擎没工作"。
即使延时 255 ms，读到的也还是爬坡过程中的瞬时值
（实测 `GAIN=0x03/AEC=0x38`，而实际画面曝光是正常的）——
**判断曝光对不对要看画面/亮度，不要只看这两个寄存器**。

### 坑 19：只改寄存器表时，`make photo` 可能复用**旧的位流**

`ov2640_cfg.hex` 是 `top_photo.json` 的依赖，但改表重生成的 hex 可能比上一次
生成的 json 更旧，`make` 就会认为目标是最新的、直接跳过重建。
结果就是"代码改了、固件没变"。改完寄存器表后强制重建：

```bash
touch top.v top_photo.v      # 或者 rm -f top_photo.json
make && make photo
```

### 坑 20：同一个串口只能被一个进程占用，端口被占用时脚本会**崩在开端口那一步**

`host_capture.py` 用的 iCELINK CDC (VID `1D50` / PID `602B`) 在 Windows 上是
一个**独占**的 COM 口。**两个测试不能同时跑**：先跑的那个还在收数据
(默认 `--seconds 200`，实测收满 480 行要 58~97 秒)，后一个去开端口会直接抛

```
SerialException: could not open port 'COM419': PermissionError(13, '拒绝访问。')
```

脚本崩在 `serial.Serial()` 这一行，**一个文件都写不出来**，屏幕上只有一行红字，
看起来像"测试突然不通过" —— 其实固件和硬件都是好的。连着双击两个 `.bat`
时必现：第一个的 `.bat` 建于 10:00:26、10:02:14 才结束，第二个 10:00:55 被双击，
端口正被占着。

现在的做法：

- `wait_port_free()` / `open_serial()` 会**等端口空出来**再继续，默认最多等
  `--port-wait 120` 秒；
- 顺序是 **先等端口空闲 → 再烧录 → 再抓图**，所以两个测试连着双击也不会互相打断；
- 脚本最后会打印 **VERDICT**：
  - `480/480` 行全齐 → `VERDICT = OK`
  - 只缺顶部 row 0/1 (首帧没稳的已知现象，图仍可用) → `VERDICT = OK`
  - 其他缺行 → `VERDICT = FAIL` (退出码 2)

输出文件名按传感器区分：`photo-<sensor>.raw` / `.png` / `.stream`，
所以 OV2640 和 OV5640 的结果不会互相覆盖。跑哪个传感器就加
`--sensor ov2640` / `--sensor ov5640`。

## 8. 附: 诊断读的 14 步顺序

顺序固定（bank 切换必须在对应的读之前）：

| 步 | 动作 | 寄存器 | 内容 | 期望值 |
|---|---|---|---|---|
| 0 | 写 | 0xFF | 切到 sensor bank | 0x01 |
| 1 | 读 | 0x0A | 芯片 ID PID | **0x26** |
| 2 | 读 | 0x0B | 芯片 ID VER | **0x42** |
| 3 | 读 | 0x00 | GAIN (AGC 增益) | 见第 7 节第 11 条 |
| 4 | 读 | 0x10 | AEC (曝光时间) | 见第 7 节第 11 条 |
| 5 | 写 | 0xFF | 切回 DSP bank | 0x00 |
| 6 | 读 | 0xC0 | HSIZE8 (输入宽>>3) | **0xC8** (1600) |
| 7 | 读 | 0xC1 | VSIZE8 (输入高>>3) | **0x96** (1200) |
| 8 | 读 | 0x8C | SIZEL | 0x00 |
| 9 | 读 | 0x51 | HSIZE (输入宽>>2) | **0x90** (400) |
| 10 | 读 | 0x52 | VSIZE (输入高>>2) | **0x2C** (300) |
| 11 | 读 | 0xDA | IMAGE_MODE | **0x00** (YUV422/YUYV) |
| 12 | 读 | 0xC2 | CTRL0 | **0x0E** (YUV422\|YUV_EN\|RGB_EN) |
| 13 | 读 | 0x5A | ZMOW (输出宽>>2) | **0xA0** (640) |

# 拍照模式 (`top_photo`) —— 相机 → 串口 → 主机端 PNG

`top.v` 是"功能自检"：配置相机、统计 DVP 字节、打印一份诊断报表。
`top_photo` 是"拍照"：把相机看到的图像原样通过串口送出去，主机端拼成 PNG。

两个入口互不影响，默认流程 (`make`) 仍然是自检版；拍照版单独用 `make photo` 构建。

## 9.1 怎么用

```bash
cd src/basic/verilog/pmod-camera-ov2640

# 1) 构建拍照固件 (默认 115200 波特率 / 每段 8 行)
make photo

# 2) 烧录 + 收图 (在 Windows 主机上跑, 需要 pyserial + numpy + pillow)
python host_capture.py --flash --baud 115200 --seconds 200
```

主机端会打印进度，最后写出三个文件：

| 文件 | 内容 |
|---|---|
| `photo-ov2640.raw` | 拼好的原始 YUYV (640x480x2 = 614400 字节) |
| `photo-ov2640.png` | 转成 RGB 的 PNG |
| `photo-ov2640.stream` | 原始串口字节流 (排查用) |

`--flash` 会先调 `icesprog.exe` 烧录（**不要用拖拽烧录**，虚拟 U 盘不可靠），
然后自动找 iCELink 的 CDC 串口 (VID_1D50 / PID_602B) 收数据。

实测（2026-11-22）：**约 58 秒收满 480 行 / 60 段，0 个 CRC 错误**。

## 9.2 为什么要"分段扫描"

640x480 YUYV 一帧 = 614400 字节，而 iCE40UP5K 全部 BRAM 只有 30 x 4Kbit = 15KB，
**整帧根本存不下**，而且串口 115200 只有 11520 字节/秒，
相机一行数据（33MHz 下 38us）就过去了。

所以改成"分段扫描"（band scan）：

- 每段采 `KROWS = 8` 行（10240 字节，20 个 BRAM 块）存进片上缓冲；
- 串口慢慢把这 8 行发出去（8 x 1280 = 10240 字节，888ms）；
- 发完再采下一段，**下一段从下一帧的行 `seg*8` 开始采**（相机一直在出流，
  我们只在需要的那几行存数据，其余帧丢掉）；
- 主机端按行号把 60 段拼成一整幅图。

一行必须在 38us 内连续采完（一行 1280 字节），所以串口发一行要 111ms，
**不可能边收边发**，缓冲是唯一出路。

段起始行号在**帧边界（VSYNC 上升沿）**重新武装，这样行号和帧永远对得上，
不会采到半行或者上一帧的残留。

## 9.3 串口协议

每行一个包：

```
A5 5A            magic (主机端靠它重新同步)
row_lo row_hi    行号 (小端, 16 位)
len_lo len_hi    本行数据长度 (小端, 16 位, = 1280)
data[len]        原始 YUYV 字节
crc_lo crc_hi    CRC16/CCITT-FALSE (poly 0x1021, init 0xFFFF)
```

- CRC 覆盖范围 = `行号(2) + 长度(2) + 数据`，**不含 magic**；
- 状态包用 `row = 0xFFFF, len = 16` 承载遥测（诊断码 / flags / 段号 /
  已采行数 / 已采字节数 / 末行字节数），每段之后发一个，方便看 FPGA 在干什么；
- 复位后立刻发一个"上电信标"状态包（诊断码 = 3），
  主机端一收到它就知道比特流跑起来了，后面没数据就是采集/配置问题，不是链路问题。
